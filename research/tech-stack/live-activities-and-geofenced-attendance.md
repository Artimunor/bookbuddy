# Live Activities and geofenced attendance

**Decision, 23 November 2026:** Start with deliberate W‑06 check-in/out and optional shift status on the Lock Screen. Pilot location-based reminders only if the device, privacy and store gates below pass. Do not turn a phone’s boundary crossing into a working-time entry, a payroll decision or permission to start work. The selected [Expo/React Native stack](../../docs/reports/2026-11-23-mobile-tech-stack.md) and [W‑06 design](../../design/screens/worker/W-01_W-09-specs.md#w-06--check-in-or-out) currently use a foreground location fix for a deliberate action and no background monitoring; the reminder would be a separately reviewed change.

The sources below were consulted on 23 November 2026; publication or platform dates are noted where relevant. `[unverified]` means the behavior, approval or legal determination has not been established for BookBuddy. No device test was performed for this note.

## iOS: ActivityKit displays the shift; Core Location detects proximity

### Starting, updating and ending the Live Activity

- **Local start:** Ordinary `Activity.request` is a foreground operation. Receiving an entry event may wake the app, but does not make it foreground or authorize a direct background `request`. iOS 17+ has a separate path when the system executes a `LiveActivityIntent`, such as a worker invoking an App Shortcut or supported system control. Calling an intent’s `perform()` from a geofence callback is not a documented substitute for system invocation. The reliable design path is a local arrival notification that opens W‑06, then a foreground start on explicit check-in. See [ActivityKit lifecycle](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities#Start-the-Live-Activity) and [`LiveActivityIntent`](https://developer.apple.com/documentation/appintents/liveactivityintent).
- **Server start:** Since **iOS 17.2**, the server can send a `start` event through APNs to an ActivityKit **push-to-start token**, without the worker opening the app at that moment. The app must have obtained and registered the token beforehand and keep it current. Use the `liveactivity` push type, the app bundle’s `.push-type.liveactivity` topic and the documented attributes and start alert. Update/end normally use a separate token scoped to the running activity; rotate and invalidate old tokens. On iOS 17.1 and earlier, APNs can update/end an already started activity, not remotely start it. The server does not receive Core Location events from Apple: starting on entry would first need eligible device-to-server delivery and then APNs delivery. That adds failure modes and data sharing; do not build that round trip just to show an arrival prompt. See [Apple’s ActivityKit push guide](https://developer.apple.com/documentation/activitykit/starting-and-updating-live-activities-with-activitykit-push-notifications).
- **Lifetime:** A standard Live Activity is active for at most **8 hours from start**. iOS then ends it and removes it from the Dynamic Island; the final snapshot may remain on the Lock Screen for up to **4 more hours** (at most **12 hours visible**, not 12 hours active). Workers and the app can end or dismiss it sooner. An eight-hour workday with a lunch break or a prompt that started before check-in can outlast the activity. Do not chain activities to manufacture a permanent timer; stop rendering elapsed time in an ended/stale view and keep W‑06 available throughout. At checkout send final state and dismiss promptly. See [Apple’s lifetime and dismissal rules](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities#Plan-for-Live-Activity-duration-and-asset-constraints) and the [HIG](https://developer.apple.com/design/human-interface-guidelines/live-activities).
- **Updates and budgets:** The app can call `Activity.update`/`end` while it is running, including if granted background runtime; this does not grant it runtime when suspended. Apple publishes an hourly budget for high-priority ActivityKit pushes but no fixed numerical allowance in the guide. Priority `10` (the default) counts and can be throttled; priority `5` does not count toward that budget but delivery is best effort, not immediate or guaranteed. `NSSupportsLiveActivitiesFrequentUpdates` enables higher-frequency use; workers can turn it off, observable through `frequentPushesEnabled`. Apple documents no equivalent hourly APNs quota for local updates. Keep attributes plus state under **4 KB**, use source timestamps and a stale date, and send changes only, not timer ticks. The extension itself cannot access the network or receive location updates. See [Apple’s push frequency and stale-state guidance](https://developer.apple.com/documentation/activitykit/starting-and-updating-live-activities-with-activitykit-push-notifications#Determine-the-update-frequency) and [ActivityKit constraints](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities#Plan-for-Live-Activity-duration-and-asset-constraints).
- **UI and actions:** Ship a signed native **WidgetKit extension** (Swift/SwiftUI, directly or generated by Expo) and `NSSupportsLiveActivities` on the app. Design Lock Screen and compact, minimal and expanded Dynamic Island presentations; iPhones without the Island still have Lock Screen presentation and can show selected alerts as a banner. iOS 17+ supports a SwiftUI button/toggle backed by App Intents in the expanded/Lock Screen views; authentication/unlock is required when the device is locked. An actual **Check out** `LiveActivityIntent` is feasible, but should commit only if it can uphold W‑06’s session, authorization, confirmation, location and offline semantics. For the pilot, use a **Check out** link to W‑06, not a lock-screen mutation, and keep the native button conditional on a separate proof. Use a link, not an intent button masquerading as one. See [Apple HIG](https://developer.apple.com/design/human-interface-guidelines/live-activities) and [WidgetKit interactivity](https://developer.apple.com/documentation/widgetkit/adding-interactivity-to-widgets-and-live-activities).

### Region monitoring and review

- **Relaunch:** `CLMonitor` with a circular geographic condition is the modern API; `CLLocationManager` with `CLCircularRegion` is the legacy API. The OS can wake a suspended app or try to launch a system-terminated app in the background for entry/exit with effective **Always** authorization. Recreate a `CLMonitor` with its previous identifier and resume consuming events; test restoration after reboot and first unlock. Apple’s archived region guide (21 March 2016) says Background App Refresh off prevents region notification wakes. Do not promise delivery following a user swipe-to-force-quit; exact behavior by API/OS and settings is `[unverified]`. Compare the [current Core Location monitoring guide](https://developer.apple.com/documentation/corelocation/monitoring-the-user-s-proximity-to-geographic-regions), [authorization matrix](https://developer.apple.com/documentation/corelocation/requesting-authorization-to-use-location-services) and [legacy region guide](https://developer.apple.com/library/archive/documentation/UserExperience/Conceptual/LocationAwarenessPG/RegionMonitoring/RegionMonitoring.html).
- **Bounds and quality:** **20 simultaneous conditions per app** for `CLMonitor`; the legacy region cap is also 20. Apple shows a 200 m example, not a guaranteed radius or accuracy. The archived guide describes a system-defined boundary cushion and a dwell threshold (at least 20 seconds in that historical guidance); do not treat it as a modern SLA. Apple’s `CLLocationManager` [accuracy authorization documentation](https://developer.apple.com/documentation/corelocation/cllocationmanager/accuracyauthorization) says reduced accuracy cannot use region monitoring. A crossing can be late or missed at nearby sites, indoors or with weak positioning. A state report on registration is not necessarily an arrival: legacy Core Location does not synthesize an entry just because registration happens inside the circle; Expo reports initial state at startup. Neither proves a worker crossed a gate at the recorded time.
- **Permission flow:** Request **When In Use** at the first foreground attendance use, then explain and request **Always** only when someone enables background reminders. Supply `NSLocationWhenInUseUsageDescription` and `NSLocationAlwaysAndWhenInUseUsageDescription`. After a durable When In Use grant, iOS offers a one-time upgrade request; **Allow Once** can suppress it. A direct Always request may report provisional Always, with the real upgrade prompt deferred; do not infer delivery from that status. Leave foreground entry and a no-location alternative available. See [Apple’s Always flow](https://developer.apple.com/documentation/corelocation/cllocationmanager/requestalwaysauthorization()) and [authorization guide](https://developer.apple.com/documentation/corelocation/requesting-authorization-to-use-location-services).
- **App Review:** [Guidelines §§2.5.4, 5.1.1 and 5.1.5](https://developer.apple.com/app-store/review/guidelines/#privacy) restrict background services to intended purposes, require relevant location use, notice and permission, and favor minimization and alternatives. Use purpose strings that say what happens when the app is closed, privacy disclosures matching actual processing, and reviewer notes/demo for opt-in, off, and the manual path. Don’t use a continuous location mode to keep JS or a display alive. Review acceptance is `[unverified]`.

## Android: ongoing notification first; promotion is optional

- **Display:** Post an ongoing notification on the worker’s attendance channel using `setOngoing(true)` and an authenticated route to W‑06. Android 13+ uses runtime `POST_NOTIFICATIONS` for ordinary notifications; channels, user settings and OEM behavior control visibility. Android 14 lets users swipe away most ongoing notifications while unlocked. Dismissal is not checkout and should not cause immediate re-posting. A native chronometer (`setWhen`/`setUsesChronometer`) can display elapsed time without polling. See [Android notification permission](https://developer.android.com/develop/ui/views/notifications/notification-permission), [Android 14 dismissal changes](https://developer.android.com/about/versions/14/behavior-changes-all#non-dismissable-notifications) and [`Notification.Builder`](https://developer.android.com/reference/android/app/Notification.Builder#setUsesChronometer(boolean)).
- **Android 16 / API 36 Live Updates:** Request a **promoted ongoing notification** only for an ongoing, user-initiated, time-sensitive activity worth watching as it changes. Declare `POST_PROMOTED_NOTIFICATIONS` (non-runtime), request promotion, set ongoing and a title, and use an allowed system style and non-minimum channel with no custom `RemoteViews`, colorization or group summary. The system, user and OEM decide whether it appears as a Live Update or status chip; a normal notification is the fallback. A routine shift clock or passive arrival nudge is not a good default candidate. Whether a particular time-sensitive, worker-started phase qualifies is `[unverified]`; don’t promise Dynamic Island equivalence. See [Android’s Live Update requirements and use criteria](https://developer.android.com/develop/ui/views/notifications/live-update).
- **Foreground services are separate:** Neither an ongoing notification nor a Play services geofence requires a long-running foreground service. A real continuous location feature would need the `location` foreground service type and, for Android 14+ targets, `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_LOCATION`; it also needs location enabled and runtime coarse/fine access. Starting while backgrounded is separately restricted; a geofence transition is a documented background-start exemption, but does not by itself satisfy the location while-in-use restriction (normally needs `ACCESS_BACKGROUND_LOCATION` to start from background). Don’t use `dataSync`, `specialUse` or `location` to keep a shift timer alive. See [foreground service types](https://developer.android.com/develop/background-work/services/fgs/service-types#location) and [start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start).
- **Geofencing:** Google Play services’ `GeofencingClient` accepts **100 active geofences per app, per device user**. It supports entry, exit, dwell and expiration, with `PendingIntent` delivery to a `BroadcastReceiver`. Google suggests a **100–150 m** minimum radius for best results. It gives **2–3 minutes on average** under background location limits and examples of up to **6 minutes** after prolonged stationary use, not a hard bound. Poor network-derived location or too small a radius may miss the transition. Doze limits Wi-Fi scans, network and scheduled jobs; separate local delivery from any upload, and measure both rather than claiming a separate guaranteed Doze latency. Re-register still-valid fences after reboot where appropriate. Android 15+ cancels pending intents on user Force Stop; honor that, and treat Recents removal and ordinary process death as separate cases with OEM variance. See [geofencing and latency](https://developer.android.com/develop/sensors-and-location/location/geofencing), [Doze/App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby) and [Android 15 stopped-state behavior](https://developer.android.com/about/versions/15/behavior-changes-all#enhanced-stop-states).
- **Permissions and Play:** Ask for foreground location first. Geofencing requires `ACCESS_FINE_LOCATION` and, for modern targets, `ACCESS_BACKGROUND_LOCATION`; an approximate-only foreground grant is not sufficient. On Android 11+ the worker enables **Allow all the time** in Settings after a clear, declinable explanation. Google Play requires background location to deliver significant user benefit and be necessary to core functionality. A convenience-only reminder in a multipurpose app is a material rejection risk, even if opt-in. The Play Console declaration covers one essential feature, with a device demo video, prominent in-app disclosure before OS permission explaining closed-app location, store disclosure and privacy-policy links in app/listing; keep Data safety accurate. If not approved, remove the manifest permission and background feature from release tracks; a runtime flag alone is insufficient. See [Android background permission flow](https://developer.android.com/develop/sensors-and-location/location/permissions/background) and [Google Play declaration guidance](https://support.google.com/googleplay/android-developer/answer/9799150?hl=en).

## Spain and EU: an arrival signal is not the working-time register

**Current duty.** [RD‑ley 8/2019, 8 March 2019, art. 10](https://www.boe.es/buscar/act.php?id=BOE-A-2019-3481#ar-10) added [Workers’ Statute art. 34.9](https://www.boe.es/buscar/act.php?id=BOE-A-2015-11430#a34). The employer must record each employee’s actual daily start and end times, keep the record for **four years**, and make it available to the worker, legal representatives and the Labour and Social Security Inspectorate. Organize/document the process through collective bargaining or company agreement, or, failing that, an employer decision after consulting legal worker representatives. [CJEU C‑55/18 (14 May 2019), para. 60](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:62018CJ0055) requires an objective, reliable and accessible means of measuring time actually worked. Neither source makes GPS necessary. An attendance event can feed the employer’s register if it captures actual working time with correction, audit and access; a geofence **alone** does not reliably do that. A phone can arrive before work, stay parked while a person leaves, or miss working travel between sites, work elsewhere, waiting time and breaks. Do not treat elapsed on-site time as payable hours or silently overwrite a disputed record. The [AEPD employment guide, pp. 35–36, 53–54 (updated December 2025)](https://www.aepd.es/guias/la-proteccion-de-datos-en-las-relaciones-laborales.pdf) explicitly distinguishes when work starts/ends from where a worker is at any moment.

**Digital reform.** Congress [returned the earlier bill](https://www.congreso.es/public_oficiales/L15/CONG/BOCG/A/BOCG-15-A-58-3.PDF) on 10 September 2025. A separate [Ministry draft Royal Decree](https://expinterweb.mites.gob.es/participa/listado/download/6cb63e79-48a8-4e99-9784-3a0b26ae6106), put on an urgent track on 30 September 2025, proposes digital, personal and direct entries, authentic and traceable changes, and accessible records. A [Ministry consultation on technical and security rules](https://expinterweb.mites.gob.es/participa/listado/download/4d13dbda-6be7-4ad5-b224-4269a9f4fad4) ran 7–30 March 2026. The [Council of State docket](https://www.consejo-estado.es/transparencia/dictamenes-estudios-y-memorias/asuntos-despachados/comision/trabajo-y-economia-social-65/) records opinion 188/2026 on 19 March 2026; the [opinion itself (copy hosted by Laboral Social), p. 102](https://www.laboral-social.com/sites/laboral-social.com/files/188_2026.pdf#page=102) concludes that the draft should not be approved as proposed. The BOE consolidation updated 18 November 2026 retains art. 34.9’s existing wording; no final digital-record decree was verified in the official sources consulted. Treat the requirements above as draft, with final publication and timing `[unverified]`, and recheck BOE before launch. Do not market the app as a compliant statutory register before employer/counsel sign-off.

**Lawful basis and notice.** [GDPR, 27 April 2016](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng) treats identifiable location as personal data (art. 4). Document necessity, purpose and retention (arts. 5–6), inform workers (arts. 12–14), restrict access and adopt privacy by design (arts. 25, 32), and assess high risk under art. 35 before deployment. Separate the statutory record (normally art. 6(1)(c), not employee consent) from optional location processing. [Workers’ Statute arts. 20.3 and 20 bis](https://www.boe.es/buscar/act.php?id=BOE-A-2015-11430#a20) pair employer oversight powers with dignity, privacy and digital disconnection. [LOPDGDD, 5 December 2018, arts. 87–91](https://www.boe.es/buscar/act.php?id=BOE-A-2018-16673#a8-9) cover privacy on employer-provided devices (87), disconnecting outside work (88), video/audio separately (89), lawful and limited employee geolocation (90), and additional collective-agreement safeguards (91). Art. 90 requires **prior, express, clear and unequivocal** information to employees and, where applicable, representatives: how monitoring works and the rights of access, rectification, restriction and erasure. Explain the controller, purpose/basis, recipients, timing, retention and correction route in plain language workers understand. An OS permission or in-app switch is not that notice, nor is it by itself GDPR consent.

- **Employees of crew businesses:** The employer is normally the controller for timekeeping; BookBuddy may be its processor for that purpose under an art. 28 agreement, but assess separately any purpose BookBuddy decides for itself. The AEPD links legitimate labor oversight to the employment contract and statutory control powers, not consent, and requires a less intrusive method where equally effective. Do not use art. 34.9 to justify background geolocation by default. Do not rely on employee consent for monitoring given the power imbalance. Make the product switch voluntary and revocable without loss of shifts, pay or convenience needed to record work. Provide a usable alternative without requiring a worker’s personal phone.
- **Genuinely self-employed workers:** Art. 34.9 does not generally make an independent contractor record their own hours as an employee; a subcontractor’s employees still need their employer’s register. Labels are not decisive if the relationship is really employment. The GDPR still applies: explain processing and pick a lawful basis for the specific optional purpose. Necessary contract performance (6(1)(b)) or a justified and balanced legitimate interest (6(1)(f)) is not established by simply writing a term. Consent (6(1)(a), art. 7) is plausible only where there is genuine free choice, comparable no-location access and easy withdrawal, and the platform rules below do not rule it out. Allocation of data roles, applicable collective agreements and the lawful basis for a specific pilot are `[unverified]` pending local review.

**Platform work.** [Directive (EU) 2024/2831, 23 October 2024, arts. 1–2, 7–11, 13–14 and 29](https://eur-lex.europa.eu/eli/dir/2024/2831/oj/eng) sets transposition by **2 December 2026**. [EUR-Lex’s national measures listing](https://eur-lex.europa.eu/legal-content/EN/NIM/?uri=CELEX:32024L2831) listed zero Spanish notifications at review; this is not proof of no national action. Spain’s implementing text/status and BookBuddy’s classification are `[unverified]`. Selling scheduling software to employers is not by itself operating a digital labour platform. Matching workers to jobs, allocating work or managing work through automated systems could change the analysis; the test is what BookBuddy does in each model, not whether it calls itself a marketplace. The relevant data protections extend to platform workers without an employment contract as well. Art. 7 bars automated systems from collecting data while people are not offering or performing platform work, among other restrictions; signed-up and actually offering/performing are not interchangeable. Recital 39 rejects reliance on platform-worker consent in this context. Art. 8 requires a GDPR impact assessment with worker input; arts. 9–11 cover transparency, portability, human oversight and review, with a human decision for restrictions, suspension, termination or equivalent detriment. Art. 11 has a business-user exception; it does not erase the other safeguards. Don’t infer lateness, deny shifts or pay, or make adverse decisions from a passive phone signal. A worker-only, local prompt with no employer-visible monitoring reduces risk but does not by itself settle scope or legality.

## Product design and real-device gates

1. **Ship attendance without background permission first.** W‑06 takes one foreground fix when the worker deliberately checks in/out, where configured and authorized; evaluate it on device and discard coordinates unless a documented necessity requires otherwise. If background permission is declined, W‑06 and optional scheduled reminders still work. If foreground location is denied, accuracy inadequate, offline evidence cannot be queued, or the worker has no suitable phone, offer an employer-approved location-free manual entry or foreman-assisted exception (not a fake geofence success), capture the actual time and make it correctable. Notification/Live Activity permission, dismissal, expiry or missing hardware never blocks recording. Keep attendance, statutory timekeeping and safety acknowledgment distinct.
2. **Make reminders opt-in, off by default, separate from status display.** For a confirmed assignment only, and only during a legally approved, explicitly activated short window, let the OS watch the assigned site and deliver a coarse boundary signal. Start with **entry** → one expiring local notice: “At your site? Open to check in.” An initial inside-state can suggest checking in but is not a crossing. Do not register exit for the pilot unless a departure reminder justifies it; any exit remains a suggestion, never a checkout. Handle neighbouring jobs and drive-bys without choosing a shift silently. Remove fences at check-in, cancellation, sign-out, opt-out or permission loss as applicable. Use native expiration where supported; Apple’s documented [`CLMonitor` interface](https://developer.apple.com/documentation/corelocation/clmonitor) has no fence expiry. Prove that the lawful window can be enforced with the app suspended or terminated; dropping a callback is not the same as stopping OS monitoring. If this cannot be established, or the approved purpose cannot cover arrival before work, leave background reminders off and use scheduled or foreground reminders. No continuous GPS, server crossing history or coordinate/transition analytics. The OS still uses device location to detect the boundary; the app gets a transient transition, not a location stream. A local reminder requires **zero** backend requests or writes.
3. **Show status after deliberate check-in.** On iOS start locally; on Android use an ongoing notification. Show shift/reference, an innocuous site alias (never an address, access code or customer name), start time and an OS-rendered elapsed timer labelled “Since check-in,” not “hours worked.” Show “Safety hold — open app” where warranted and never show a Lock Screen all-clear. Set a stale date on iOS; on Android use an OS notification timeout if the app cannot refresh reliably. Provide one **Check out** action to the authenticated W‑06 flow; use a native direct intent only if separately proven. Separate “Saved on this device · pending sync” from confirmed status; W‑06’s event time, stable operation ID, ordering and receipt rules still apply. Dispatch at most one status update per relevant change, none for elapsed ticks; keep ordinary attendance and hold/escalation paths independent of push. Restrict employee records to authorized audiences and retention; do not put transient location evidence under the register’s four-year retention by default.
4. **Budget battery through design.** Geofencing can use lower-power OS location sources than continuous high-accuracy sampling. With a single armed site, no service to hold the app awake, no polling and an OS-rendered clock, incremental draw should be lower than continuous tracking; BookBuddy’s absolute cost is `[unverified]`. Keep coverage small and update displays only when the state changes.

**Proposed device spike acceptance (not measured and not a field SLA).** Use signed release-like builds with the actual Expo SDK, extension signing and push credentials on a Dynamic Island iPhone, a supported iPhone without it, and a Pixel and at least one other pilot Android OEM/model. Cover Android 16 promotion only if pursuing it and an older supported Android for the ordinary path. Use real Costa Blanca routes: rural weak signal, dense/neighbouring sites, drive-bys, walking and indoor entry. Record crossing time independently and distinguish OS callback, local notice, remote delivery and deliberate user act.
