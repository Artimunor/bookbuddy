# React options for the BookBuddy app

**Decision within the React family: use React Native with Expo for the iPhone and Android crew app, and offer a responsive web portal for customers from day one.** Start with native `StyleSheet` and shared design tokens. Use ordinary Tailwind where the UI is HTML. Capacitor is the credible alternative if sharing the booking UI outweighs the work of integrating and maintaining native field features. A pure PWA is a good customer surface, not a good sole dispatch client: on iPhone, push starts only after Home Screen installation and opt-in, and Safari has no general-purpose Background Sync. [WebKit Home Screen push, 16 Feb 2023](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/) · [WebKit SyncManager status](https://bugs.webkit.org/show_bug.cgi?id=182565)

Evidence cut-off: **23 November 2026**. For living docs, policies and price sheets without an explicit date below, this is the access date, not the original publication date. Vendor and developer case studies establish what was shipped at the time of reporting, not current versions or results for BookBuddy. Scores are engineering judgements, not measurements. No device tests or performance benchmarks were run.

## What matters for this product

An owner abroad should be able to request a repair, approve a quote, see updates and pay from a desktop link without installing anything. The foreman and crew need to consult the current schedule, respond to cover requests, check in and capture evidence on a site with patchy connectivity. The technology should protect the original instruction, show any translation next to it, and distinguish an action saved on the phone from one confirmed by the service. In particular, a worker's offline acceptance is **pending** until the server validates the offer, its expiry and whether someone else has already been assigned. ## 1. React Native with Expo

**Maturity.** [Expo SDK 58, released 15 Oct 2026](https://expo.dev/changelog/sdk-58), targets the iOS 27 SDK and pairs with React Native 0.88, the latest active minor on the [React Native release schedule](https://reactnative.dev/releases/overview). Its [documented device floors](https://docs.expo.dev/versions/v58.0.0/#support-for-android-and-ios-versions) are iOS 16.4+ and Android 7+; individual plugins may require newer versions. The New Architecture is mandatory from React Native 0.82 and Expo SDK 55. Fabric is the native renderer; JSI and TurboModules change how JavaScript and native code interoperate. Check the exact SDK/RN/plugin combination: an old bridge-only library is not a reason to downgrade a new project. Use a **development build** with the app's own plugins, permissions and push credentials, not Expo Go as the acceptance environment. Expo can generate native projects with config plugins, and custom Swift/Kotlin modules are possible without replacing the framework. [React Native architecture, 23 Oct 2024](https://reactnative.dev/blog/2024/10/23/the-new-architecture-is-here) · [Expo compatibility guidance, 17 Nov 2026](https://docs.expo.dev/guides/new-architecture/) · [Development builds](https://docs.expo.dev/develop/development-builds/introduction/) · [Expo Modules API](https://docs.expo.dev/modules/overview/)

**Router and performance.** Expo Router gives routes URLs and supports native navigation, web output and links across platforms. SDK 58 makes web server rendering, data loaders and middleware stable, as well as native tabs; it now defaults web output to server-rendered HTML if output is unset. Choose the deployment mode deliberately rather than accidentally taking on a web server. React Native renders native views rather than a page inside a WebView. Expect good headroom for job lists, chat and photo previews, but JavaScript work, re-renders and image decode still matter: virtualise long lists, serve thumbnails, and pass file URIs to upload code instead of moving full media through JavaScript. Use large original-plus-translation chat threads and several queued uploads as the workload, not framework demos or vendor microbenchmarks. [Expo SDK 58 Router notes, 15 Oct 2026](https://expo.dev/changelog/sdk-58#expo-router-stable-data-loaders-and-native-tabs-improved-core) · [React Native performance guide](https://reactnative.dev/docs/performance) · [Expo file uploads](https://docs.expo.dev/versions/v58.0.0/sdk/filesystem/)

**Desktop sharing.** Share TypeScript contracts, booking rules, validation, locale catalogs, tokens and selected UI with Expo Router and React Native Web where the same interaction works. Use web-only React DOM for any quote editor, desktop calendar, table, file drop or keyboard-heavy flow that is better in semantic HTML. A separate React DOM/Tailwind portal can use the same packages if server rendering and native routing should be released independently. Sharing canonical HTTPS paths and business rules matters more than making both layouts use the same components. [Expo web support, 2 Nov 2026](https://docs.expo.dev/workflow/web/)

**Production evidence.** Awaze's engineering manager reports shipping the **cottages.com, Hoseasons and NOVASOL** guest apps with Expo and Expo Router; NOVASOL needed more than ten locales, and the initial search/booking journey reused web screens in WebViews ([26 Jun 2025](https://expo.dev/blog/one-codebase-three-brands-how-awaze-shipped-3-enterprise-apps-fast-with-expo)). **SWSH** is a recent example of photo-sharing and shared delivery to iOS, an App Clip, Android and web ([26 Aug 2026](https://expo.dev/blog/inside-swsh-automated-mobile-release-pipeline-with-expo)). These are evidence for release tooling and sharing, not for durable site uploads.

### What “React with Tailwind” means on native

React DOM + Tailwind means classes resolve to **actual browser CSS**. React Native `View` and `Text` on iOS and Android are not HTML and do not run a CSS cascade. A native styling layer maps a supported utility subset to native styles, or provides a similarly concise way to author styles. Even common utilities can have different defaults for flex direction and sizing, and web-only behaviours such as hover cannot replace native press, focus and selection behaviour. Share tokens and semantics, not an assumption that a Tailwind web component or plugin can be pasted into native code. These libraries do not change the native-feature matrix, store rules, or translation architecture. [NativeWind platform differences, 30 Mar 2026](https://www.nativewind.dev/docs/core-concepts/differences) · [Tamagui utility resolution](https://tamagui.dev/docs/core/tailwind)

## 2. Capacitor + React + Tailwind, optionally Ionic React

**Maturity.** Capacitor is the native shell and plugin bridge; Ionic React is an optional UI kit of web components, not the runtime. The supported baseline is [Capacitor 8.6.2, 12 Nov 2026](https://github.com/ionic-team/capacitor/releases/tag/8.6.2), with [iOS 15+ and Android 7+ device floors](https://capacitorjs.com/docs/updating/8-0). [Capacitor 9.0.0-rc.0, also 12 Nov](https://github.com/ionic-team/capacitor/releases/tag/9.0.0-rc.0), is a prerelease. [Ionic Framework 9.0.13, 20 Nov 2026](https://github.com/ionic-team/ionic-framework/releases/tag/v9.0.13), is stable; the two projects have independent version numbers. React and Tailwind here render real HTML and CSS. Tailwind classes style app-owned markup; for encapsulated Ionic components, use the component's documented CSS variables or exposed shadow parts. Bundle the app's web assets with the binary so the shell itself can start offline. [Ionic React](https://ionicframework.com/docs/react/overview) · [Ionic CSS variables](https://ionicframework.com/docs/theming/css-variables) · [Shadow parts](https://ionicframework.com/docs/theming/css-shadow-parts) · [Capacitor sync workflow](https://capacitorjs.com/docs/basics/workflow)

**Performance and sharing.** The UI runs in WKWebView on iOS and the platform WebView on Android. This should be enough for booking forms and a bounded job inbox; that is an expectation, not a benchmark. Long message timelines, keyboard and safe-area behaviour, photo previews and large media passed over the native bridge are the risks. Keep blobs out of Base64/JSON, hand paths to native transfer code, and window long lists. Of the store-distributed choices here, it is the best fit for sharing semantic HTML, Tailwind and UI behaviours with a desktop portal. Use responsive desktop layouts and explicit adapters for native plugins; a working Chrome tab doesn't prove that the same code works in WKWebView, or that a browser-only plugin has a native implementation. [Capacitor iOS platform](https://capacitorjs.com/docs/ios) · [Android platform](https://capacitorjs.com/docs/android) · [Plugin platform adapters](https://capacitorjs.com/docs/plugins/web) · [Capawesome file handling](https://capawesome.io/blog/capacitor-file-handling-guide/)

**Production evidence.** **Paperwork**, a Dutch bookkeeping app with camera capture and biometric unlock, publishes a [production code snapshot using Ionic React and Capacitor](https://github.com/HenryCordes/paperwork-app-public); both [App Store](https://apps.apple.com/us/app/paperwork/id6746358088) and [Play Store](https://play.google.com/store/apps/details?id=nl.paperwork.app) list an August 2025 release. **MyBodyTutor** uses Ionic and Capacitor for coaching messages, photo logging and reminders on both stores; its published UI is Angular, and offline support was future work at the time ([case study with CTO interview, 20 Jul 2025](https://capawesome.io/blog/showcase-mybodytutor/)). **BBC Children's Games** documents native and web delivery with Capacitor ([Ionic case study](https://ionic.io/resources/case-studies/bbc-games)). The current Capacitor 8 + Ionic React/Tailwind combination under BookBuddy's field workload remains **[unverified]**.

## 3. Pure React/Tailwind PWA

**Maturity and performance.** A responsive HTTPS web app gains installability with a web manifest and offline behaviour through a service worker, caches and local data. It follows browser capabilities, not a single SDK release. WebKit added Home Screen push in iOS/iPadOS 16.4 (2023), Declarative Web Push in Safari 18.4 (2025), and enabled “Open as Web App” by default when adding to the Home Screen in Safari 26 (2025); none of these makes an ordinary iPhone tab eligible for push. Current WebKit release notes reviewed include [Safari 27.2, 26 Oct 2026](https://webkit.org/blog/18515/webkit-features-for-safari-27-2/). On iOS users follow Add to Home Screen and then actively opt in from the installed app; on Android capable Chromium browsers can provide install promotion and Web Push. A lightweight portal can be fast to open from a link and serve cached screens on repeat visits; the cold first visit still needs the network, and large DOM lists and media still need optimisation. Mobile and desktop share the whole web stack, with responsive UX rather than different runtimes. [PWA platform guidance](https://web.dev/learn/pwa/progressive-web-apps) · [Install UX](https://web.dev/learn/pwa/installation) · [iOS push, 16 Feb 2023](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/) · [Declarative Web Push, 27 Mar 2025](https://webkit.org/blog/16535/meet-declarative-web-push/) · [Safari 26, 15 Sep 2025](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)

**Production evidence.** **Excalidraw** moved from an Electron wrapper to an installable web app ([maintainer account, 17 Dec 2020](https://plus.excalidraw.com/blog/deprecating-excalidraw-electron)); its [current project README](https://github.com/excalidraw/excalidraw#excalidrawcom) documents offline PWA use, local saves and live collaboration. Google documents **MakeMyTrip** deploying a booking PWA ([Chrome/web.dev case study](https://web.dev/case-studies/make-my-trip)); its current PWA configuration **[unverified]**. These show production web distribution for collaboration and booking, not reliable closed-app work on iPhone.

Two design rules matter more than framework selection:

1. **Dispatch is a server workflow.** Store and acknowledge assignments on the server. If nobody acknowledges by the operational deadline, notify the foreman/operator through a separately agreed escalation channel. Push should carry a link to the current job/offer, not property details or instructions on a lock screen. Keep chat messages durable with stable client IDs, reconciliation and role-scoped access; receipts and sockets do not establish that a human read the message.
2. **Durable capture is not guaranteed background delivery.** Persist metadata and app-owned files before saying “saved”. Show queued, failed and sent states. Retry on foreground/reconnect with idempotency and a resumable upload protocol as media size warrants. On iOS the native background `URLSession` can outlive suspension or system termination, but a user force-quit cancels transfers. Android recommends WorkManager for deferred work and a user-initiated transfer job when an eligible long upload started by the user needs to continue visibly. Test system kill and explicit force-quit separately. For check-ins record time and accuracy with the user's action, and support permission denial or a weak fix without claiming the coordinate proves attendance. [Apple background sessions](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/background(withidentifier:)) · [Apple resumable transfers, WWDC23](https://developer.apple.com/videos/play/wwdc2023/10006/) · [Android transfer options](https://developer.android.com/develop/background-work/background-tasks/data-transfer-options)

## Languages, translation and accessibility

- **Interface copy:** Use human-reviewed locale catalogs, a user preference independent from phone language, plural rules and `Intl` date/currency formatting. Store job times with the site's time zone so a remote owner's display cannot move the appointment. Expo supplies locale information and RN `I18nManager`; direction changes through that native manager can require a new app start. Use logical start/end styles and verify SDK 58's iOS RTL behaviour. On Capacitor/PWA, set `lang` and `dir` on the HTML root, use logical CSS, and set language and isolate direction per message (`dir="auto"`/`bdi`) for mixed Arabic, Latin addresses, dates and numbers. Mirror only directional UI; keep the original message and its translation separately readable. [Expo localization](https://docs.expo.dev/guides/localization/) · [SDK 58 RTL change, 15 Oct 2026](https://expo.dev/changelog/sdk-58#notable-breaking-changes) · [RN I18nManager](https://reactnative.dev/docs/i18nmanager) · [W3C bidi guidance](https://www.w3.org/International/articles/inline-bidi-markup)
- **Message translation:** Start with a server-side provider available to all clients. Translate each immutable message revision once per needed target locale and share that stored result among authorised recipients; do not embed service credentials in clients or translate the same message every time it is opened. Retain source text, source locale, translated text and provenance; send the source immediately even if translation is delayed. Label translations and allow manual correction and human acknowledgement of critical instructions. Google Cloud and DeepL document Arabic support; validate the actual field vocabulary and target pairs, including dialects, and check retention, processor terms and region support before sending customer/worker text. Voice notes are recordings, not translated text: any later transcription/translation is a separate consent, language and accuracy decision. [Cloud Translation languages](https://docs.cloud.google.com/translate/docs/languages) · [Data usage](https://docs.cloud.google.com/translate/data-usage) · [DeepL languages](https://developers.deepl.com/docs/resources/supported-languages)
- **On-device option:** Native shells can wrap Google's on-device **ML Kit** for iOS and Android (Arabic listed; model downloads required; some non-English pairs pivot through English), or use Apple's **Translation** framework on supported iOS versions with a separate Android implementation. This means a native module/plugin and separate testing, not a styling option or simple Expo Go import. ## Distribution, testability and costs

**Store rules apply to both native shells.** Apple [App Review §3.1.3(e)](https://developer.apple.com/app-store/review/guidelines/#other-purchase-methods) requires a non-IAP payment method for physical goods/services consumed outside the app. [Google Play Payments §3](https://support.google.com/googleplay/android-developer/answer/9858738?hl=en) says not to use Play Billing for them. That covers the in-person booking charge or repair deposit; it does **not** classify a later paid foreman software tier, digital add-on or online group class as physical. Recheck the exact product and storefront before adding those. A processor's confirmed result should be authoritative, not the browser's return. Use store builds for changes to executable/native code or material functionality. Apple [§2.5.2 and §2.3.1](https://developer.apple.com/app-store/review/guidelines/#performance) restrict code that changes functionality and require disclosure of new functionality; its [Developer Program License Agreement, Executable Code](https://developer.apple.com/support/terms/apple-developer-program-license-agreement/) conditions interpreted code. Google [Device and Network Abuse](https://support.google.com/googleplay/android-developer/answer/16559646?hl=en) forbids out-of-store self-updates to the app/native binaries with a limited interpreter exception, not a general policy bypass. For Capacitor in particular, Apple [§4.2](https://developer.apple.com/app-store/review/guidelines/#minimum-functionality) asks for more than a repackaged site. Present the legitimate field features (offline job access, capture and push) to review, and account for content moderation for job chat under [§1.2](https://developer.apple.com/app-store/review/guidelines/#user-generated-content).
